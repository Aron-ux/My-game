# C 键人物信息页改进

[已定设计] 用户要求先提交上一轮 UI 改动，再考虑人物页；上一轮已提交为 `d77b258`。随后确定首屏优先“角色当前强弱，再查看加成来源”，保留暗金风格和角色切换，允许重排内容。先完成分析与布局示意，随后按用户“开始进行”的指令实装 A 方案。

[已定设计] 在比较两张布局探针后，用户选择 A 固定来源区。以“队伍导航 → 当前能力 → 所选条目的解释”组织页面。人物形象帮助辨认角色，属性和来源占主要阅读空间。

## 0. 决策摘要

采用 A：左侧紧凑队伍导航，中间总览，右侧固定详情。默认打开总览，点击属性在右侧查看来源。B 顶部队伍切换与属性行内展开保留为比较记录。

A 方案已实装并完成隔离运行验证。暂不增加战力评分、雷达图、无上下文的 DPS、装备槽规则或新成长系统。

## 1. 玩家、目的与约束

玩家在暂停战斗后，快速检查一个角色当前的输出、生存和循环能力，再解释某项数值如何形成。熟练玩家需要核对加成，新玩家需要理解“攻击力为什么不等于这一发伤害”。

沿用 Godot 4.6.2，1280×720 逻辑基线、最低窗口缩放与已有像素人物。保留 C / Esc 关闭、暂停恢复规则、查看角色不切换站场、普通装备赠与、阮石共享和现有技能学习规则。

## 4. 状态与机制

本轮读取角色身份、当前 / 待命状态、局内等级、运行属性、技能等级、祝福份数、装备和阮石。查看行为只改变“选中角色、页签、选中条目、展开项、滚动位置”。

不建立新的战斗状态，不计算一个会回写玩家的预览角色，不授予技能或祝福。角色查看保持只读；既有赠与入口仍由原装备系统验证并应用，成功后刷新两人的资料。

机制链：C 打开并暂停 → 默认当前站场角色 → 浏览总览 → 选择属性 → 查看来源 / 定义 → 可跳至对应技能、祝福或装备 → C / Esc 返回原暂停上下文。

## 5. 信息链与数据约束

运行时 getter → 同一口径的当前数值及可追踪来源 → 总览行 / 详情 → 玩家判断。显示不维护另一套数值规则。

来源应区分基础值、固定加值、同组加成、独立倍率、当前生效条件和最终取整。乘算项不能为了凑出相加列表而捏造成独立固定贡献。来源不足时明确说明口径，不能把未知差值归给某个祝福。

当前有按角色查询属性、装备汇总和祝福统计的函数，但没有统一逐项来源账本。需要补的是展示数据的来源说明，不是新建另一套战斗结算。不得以“先扣掉装备再加回”或临时切人来做预览。

## 6. 玩家体验

输出、生存、机动与循环帮助第一次查看的玩家定位信息；当前值配来源便于熟练玩家核对构筑。像素人物和暗金边框保留身份，主体文字采用上一轮可读的中文字体。

当前查看角色与当前站场角色分别标明。待命角色只显示其当前有效状态，不暗中模拟切入后的增益。打开面板已暂停，临时效果的剩余时间也随游戏暂停，不制作虚假倒计时。

不以这轮信息重排声称战斗更平衡、策略更多或重玩性提升；这些玩法视角不适用，因为结算和奖励均不改变。

## 7. 页面信息架构

页签建议为 **总览 / 技能 / 祝福 / 装备**。总览默认打开；人物导航始终可见。条目数量是辅助标签，不重复塞进每个标题。

A 的三个区跨页保持稳定：左侧始终为队伍；中间随页签切换为属性表、技能列表、祝福列表或装备列表；右侧始终解释当前选中项。技能页不再在右半边嵌套一层选择器与详情，祝福也不再把长说明展开到列表内。次级列表可以滚动，角色导航和选中项详情不会因此移位。

| 区域 | 常驻信息 | 按需解释 |
| --- | --- | --- |
| 身份 | 像素头像、角色名、当前站场 / 待命、本局等级 | 简短机制定位 |
| 输出 | 攻击力、普攻速度、暴击率、暴击伤害 | 基础攻速、攻击间隔、攻击力包含的加成、技能倍率边界 |
| 生存 | 当前 / 最大生命、护甲、减伤率、闪避率、生命回复 | 护甲和减伤的不同作用、来源及条件；临时生命存在时注明 |
| 机动与循环 | 移动速度、通用冷却缩减 | 生效的移动增益；单技能冷却到技能页查看 |
| 本局构筑摘要 | 已学习主动技能、祝福种类、普通装备、阮石数量 | 跳转到相应页签 |

由原 13 行整理为 11 项当前值：“基础攻速”进入普攻速度详情；“增伤”进入攻击力来源，并明确已计入攻击力。保留数值信息，减少并列时的歧义。用组标题和对齐的行列排版，不给每个数字加一张卡。

### 其他三个页签

- **技能**：9 条记录分为基础能力、主动技能、终结技，维持实际存在的记录。选中技能先讲当前效果与已有有效参数，再显示等级和下一次升级收益。5 / 10 级天赋位状态作为次级信息；效果未实装须明确标注。未学习说明从“获得技能”卡学习；不显示不可达旧配方。大招不伪造升级卡或天赋进度。
- **祝福**：团队共享 / 匹配技能两组。首行显示名称、各阶份数及可准确合并的总收益；例如“焰阳 I×2，合计攻击力 +4”。条件触发与独立减伤等不能直接相加的效果，显示逐项规则及作用范围。点击再看各阶单份说明，不让最高阶单份值冒充总效果。
- **装备**：阮石置于全队共享区，普通装备列出当前角色持有数、作用与“赠与”入口；保留右键快捷操作和原数量限制。空状态用一句话说明，不展示不存在的身体部位槽。

角色天赋 `level_talents` 若实际存在，应在技能页的已生效强化中只读显示；正式无此数据时不新增一个空天赋页，也不恢复已经停用的授予入口。

## 8. 整局生命周期

开局总览显示基础能力，未学习内容短提示；升级后能从技能页查看新增段数与参数；祝福增多后可按当前角色追查总收益；临时增益存在时显示生效条件。高密度后期内容允许列表滚动，但不把首屏关键属性重新藏回小滚动框。

Boss、死亡、结算、营地、无尽解锁等流程不变。奖励界面上打开人物页再关闭后，应仍留在奖励暂停状态。旧档中的已有强化如实读取，缺失键使用现有默认值，不迁移存档。

## 9. 边界与容易误导的地方

- 不做综合战力或单一 DPS：攻击速度、技能段数、范围、炮台持续、命中率与目标防御之间没有一个已确认的统一评分口径。
- 负护甲、零回复、零冷却缩减都是真实状态，不隐藏或替换成“正常”。绿色用于增益或改善状态，不把所有百分比自动涂绿。
- 通用冷却缩减不是每个技能最终冷却；攻击力不是最终伤害；伤害倍率不是暴击率。
- 低血触发、站场限定、到期增益需要标条件；未激活的效果不能混进当前结果。
- 选中属性的来源不能依赖鼠标持续悬停。点击或键盘聚焦可稳定读取，鼠标离开行时不消失。
- 长说明只在详情区滚动；主属性表在 1280×720 首屏容纳。小物理窗口沿项目 canvas_items 缩放，不能用缩小正文来解决逻辑布局。

## 10. 综合判断

当前页面已有角色查看、有效属性 getter、祝福份数、技能状态和装备赠与，基本能力可以复用。主要问题是有限阅读空间分配给了重复形象与框架，而高价值信息被压缩；部分文案仍在解释退役的成长路线。

改善顺序应为：先修正当前值和收益含义，再使属性首屏可读，再接来源明细与各页交叉查看，最后处理边框、字体和微交互。

## 11. 布局方案与参照

| 方案 | 空间结构 | 优势 | 代价 |
| --- | --- | --- | --- |
| 仅精修现状 | 现有三栏与嵌套滚动 | 最小改动 | 当前属性仍受大肖像、装备块挤压，来源无稳定位置 |
| A，推荐 | 窄队伍栏 + 总览 / 列表 + 固定来源详情 | 数值和解释同时可见，选中项变化不推动属性表 | 详情区占固定宽度，需要减少重复装饰 |

[A / B 视觉探针](../../design/character-info-20261013/README.md)只检验布局与风格，不是已实现页面。推荐 A 是因为本轮已确定“先看当前能力，再追来源”，固定解释位置更符合这一操作顺序。

探针复核：A 容纳全部 11 项当前值，来源与主表同时存在；B 的行内来源占用额外高度，复杂来源时更依赖主表滚动。A 的身份行还需补“本局等级”，减少说明区重复释义；B 中生成的技能图标不是现有资源授权清单，实现时须改用项目已有图标。图中文字排版不能替代 Godot 中的实际尺寸验收。

外部参照只借信息组织：

- **Grim Dawn 人物页**：官方将基础概览与详细属性分层，并通过属性悬停提供解释。借鉴“结果先行、细节按需”的层次；不复制它的装备格子与完整抗性体系。[官方角色指南](https://www.grimdawn.com/guide/character/character-basics/)
- **Last Epoch 技能说明**：官方把影响技能的属性与进一步的数值说明联系起来。借鉴“这个属性影响什么”的关联表达；本项目继续使用自己的数学规则和现有按键。[官方属性说明](https://support.lastepoch.com/hc/en-us/articles/46361892354843-Attributes)
- **本项目刚完成的技能悬停**：复用明亮中文字体、机制说明、参数、状态、适用边界的层级，不再独立维护另一套文案。

## 12. 建议的设计合同

建议 A 在 1280×720 中使用约 144 的队伍栏、约 560 的主内容和约 420 的详情区；这些是探针尺寸，实际需按容器和字体测量调整。人物名约 24，组标题 17–18，正文与数字 15–16；标签不小于 12。

默认选中攻击力，右侧立即给出来源，避免空白区只写“请选择”。换角色保留当前页签和所查属性；切技能时进入该角色仍存在的条目，缺失时选第一条可用记录。只查看角色，不发出切人动作。

来源示例来自测试机械师：基础攻击 `23.0`，焰阳 I×2 提供 `+4.0`，当前无额外倍率，攻击力为 `27.0`。旁边写明“实际伤害另受技能倍率、暴击与目标防御影响”。临时或非线性项按实际计算顺序说明，所有最终值必须与运行 getter 一致。

状态清单：初始、未学习、已学习、技能满级、天赋待选 / 已获但无效果、无祝福、多阶多份、无装备、赠与受限、待命、负护甲、临时增益、长文案、键盘焦点。无需虚构网络加载或服务器报错状态。

## 13. 验证计划与已有结果

已有证据：五张运行截图、文本与尺寸导出；现有 `character_panel_ui_smoke` 通过，输出 `CHARACTER_PANEL_UI_SMOKE_OK`，用于建立行为基线。它可以验证现有结构，不会证明改进方案易读。

实现后应验证：

1. 默认三人队伍与包含机械师的队伍均可查看；选择角色不更改 `active_role_index`、技能等级、祝福、生命与冷却。
2. 11 项当前属性首屏可读；1280×720 无横向溢出；960×540 缩放后主信息仍可辨认。
3. 来源覆盖无加成、重复祝福、混合阶数、角色专属装备、全队阮石、临时倍率、负护甲与非线性减伤，结果与运行 getter 对齐；取整只发生在显示末端。
4. 技能详情与 HUD 同口径，祝福摘要不再只显示单份最高阶，旧配方不作为正式学习指引。
5. 键盘可以切查看角色、页签和条目；C / Esc 正确恢复暂停；赠与更新来源与两人属性。
6. 人工任务：找到机械师攻击力，说明焰阳×2的收益，区分攻击力与单发伤害，查定点机炮间隔。记录耗时与误读，而非只问“好不好看”。

若必须把正文压到 12 以下、来源解释与最终值不一致、查看触发实际升级，方案即未通过。完整一局阅读节奏、跨平台字体、键盘完整流程尚待实装后验证。

## 16. 实装后回顾

- `character_panel.gd` 改为三栏四栏目；总览内容高 400，列表可见高 408，11 项核心属性无需滚动。角色图缩小，页签、队伍和来源区固定，左右内容独立滚动。
- 新增 `player_character_sheet.gd` 整理展示数据；攻击、攻速、生命、移速、减伤、闪避的可选来源追踪留在原战斗计算函数里。原有两参数调用继续使用原公式，仅人物页请求来源数组。
- 普攻、固有能力、主动技能与终结技使用现有实际参数或机制描述。未获得技能提示获得技能卡；机械师缺少的成长预览及尚未生效的天赋位明确标注。
- 祝福合计包含主属性与 `extra_stats`。焰阳 I×2 = 固定攻击 +4；神赐 I×1、II×2 = 基础生命 +55%。非线性闪避/减伤按原函数合成。
- 普通道具合计与显式赠与复用原转移验证；共享阮石不可赠与。只读查询机械师零件数量不再创建空的 `talent_runtime` 状态。
- 显式写入项目已约定的 `window/size/resizable=true` 与 `window/stretch/aspect="keep"`。这两项在基线中未写出，原配置合同检查会失败；补齐后与现有窗口行为及小窗口验证一致。
