# 游戏设计全景分析与评审流程

> 本文是 My-game 的游戏设计分析与评审方法。它规定如何从当前证据进入问题、如何完整分析、如何形成设计、如何验证，以及如何把结论交给开发。具体玩法规则仍由对应系统文档和已批准的设计记录负责。

## 1. 目标

这套流程用于回答五类问题：

1. **当前到底如何工作**：区分源码事实、设计意图、历史方案和待验证假设。
2. **为什么好玩或不好玩**：把机制变化连接到玩家认知、选择、技巧、情绪和动机。
3. **系统之间如何互相影响**：从单个机制追踪到机制链、循环、网络和生态。
4. **应该怎样改**：先定位根因，再比较保留、删减、最小修复和完整方案。
5. **如何证明设计成立**：为“能运行、看得懂、好玩、平衡、值得重玩”等不同主张匹配不同证据。

完整评审的最终产物必须能够直接支持：

- 开发组讨论与决策；
- 程序、美术、UI、音频、QA 的实现拆分；
- 验收标准与测试设计；
- 文档、路线图和变更记录同步；
- 实装后的回顾和后续迭代。

## 2. 不追求的东西

- 不用一个总分替代判断。
- 不要求每次小改动都召开大型会议。
- 不为未来可能存在的需求提前建立新系统。
- 不把代码当前行为自动视为正确设计，也不把文档描述自动视为已实现事实。
- 不用自动化测试证明“好玩”，也不用主观感受代替运行正确性和存档安全。

## 3. 何时使用完整流程

满足任意一项时使用完整评审：

- 改变核心战斗、角色轮转、资源、技能、敌人、Boss、构筑或无尽循环；
- 新增或删除玩家决策、成长轴、货币、奖励入口或永久进度；
- 改变控制、HUD 模式、教程、存档结构、难度规则或结算；
- 同时影响两个以上游戏系统；
- 设计意图、文档、UI、源码或测试之间出现冲突；
- 需要以“更好玩、更爽、更公平、更有重玩性”为理由进行修改；
- 修改可能带来显著性能、存档迁移、内容制作或发布风险。

下列情况可以使用精简评审，但仍须写清目标、证据、改动和验证：

- 单个错字或乱码；
- 不改变行为的文案同步；
- 已批准规则内的小幅数值调整；
- 明确根因且不改变设计规则的缺陷修复。

任何模板章节都不得静默留空。必须写出结论，或标记“**不适用：原因**”“**待验证：所需证据**”。

# 第一部分：证据和仓库权威

## 4. 事实、设计与假设必须分开

分析中的每个重要主张使用以下标签之一：

| 标签 | 含义 | 可作为实现依据吗 |
| --- | --- | --- |
| `[源码事实]` | 当前提交中真实可达的行为 | 可以，但仍需判断是否符合设计 |
| `[运行证据]` | 实际运行、测试、截图、日志或存档证明的行为 | 可以，注明环境和版本 |
| `[已定设计]` | 已批准但可能尚未实现的产品规则 | 可以，需列出实现差距 |
| `[提案]` | 等待评审的设计方案 | 不可以直接当作当前规则 |
| `[假设]` | 对玩家行为、体验或平衡的可检验预测 | 不可以，必须设计验证 |
| `[待验证]` | 当前证据不足 | 不可以，列出最小补证方式 |
| `[已废弃]` | 明确不再使用的历史规则 | 不可以，保留迁移说明即可 |

### 冲突处理规则

1. 源码决定“现在会发生什么”，不决定“应该发生什么”。
2. 已批准设计决定目标，不得被历史文档或残留数据替代。
3. 文档与源码冲突时，禁止把两者拼成一个不存在的混合规则。
4. 先分别记录当前行为和目标行为，再由评审决定保留、恢复、迁移或删除。
5. 没有玩家实测或行为数据时，只能说“推断可能更好玩”，不能写成“已证明更好玩”。

## 5. 仓库中的职责分工

| 位置 | 负责回答 | 不负责回答 |
| --- | --- | --- |
| 当前源码、场景和数据 | 当前可达行为、数据结构和系统边界 | 产品方向是否正确 |
| 自动化测试和运行证据 | 行为是否成立、回归是否发生 | 玩家是否觉得好玩 |
| `PRODUCT.md` | 目标玩家、产品目的、反例和无障碍底线 | 具体系统实现 |
| `DESIGN.md` | 当前 UI 视觉与交互设计系统 | 战斗和数值规则 |
| `docs/01`—`07` | 项目定位及各玩法系统规则 | 代码的完整事实证明 |
| `docs/08`—`12` | 当前状态、架构、风险和性能证据 | 新玩法的批准 |
| `docs/13`、`14` | 三层技能天赋的历史规划和内容规格 | 当前源码一定仍然可达 |
| `ROADMAP.md` | 已批准工作的优先顺序 | 当前实现状态的唯一证据 |
| `docs/design-reviews/*.md` | 单个问题的分析、方案、决定和验收 | 取代对应系统的长期文档 |
| `CHANGELOG.md` | 已发生的可见变化 | 未来计划 |
| `docs/KNOWN_ISSUES.md` | 已知但尚未解决的风险 | 默认批准风险继续存在 |
| `docs/RELEASE_CHECKLIST.md` | 发布前必须验证的行为 | 日常设计讨论 |

每份评审记录都必须写明：

- 基准提交；
- 使用了哪些文件、测试和运行证据；
- 图谱是否新于或旧于基准提交；
- 工作区是否已有与本次无关的修改；
- 哪些结论是事实，哪些只是推断。

# 第二部分：全景分析模型

## 6. 总体结构

完整模型按七层展开：

```text
L0 目标与边界
  ↓
L1 状态域与机制对象
  ↓
L2 状态变化元素
  ↓
L3 机制链、循环、网络与生态
  ↓
L4 玩家认知、能动性、技巧与情绪体验
  ↓
L5 整局生命周期、构筑、经济与重玩动机
  ↓
L6 制作成本、技术风险、验证与发布
```

低层回答“发生什么”，高层回答“玩家为何在乎、团队能否可靠实现”。任何设计若只完成其中一层，都不能进入正式实现。

## 7. L0：目标与边界

先回答：

### 7.1 玩家

- 目标玩家是谁？
- 他们熟悉幸存者 Like、动作游戏或角色切换系统吗？
- 本次设计面向新手、熟练玩家还是高 N 层玩家？
- 单局预期时长、操作强度、阅读负担和失败容忍度是什么？

### 7.2 核心承诺

- 玩家在 30 秒内应该感受到什么？
- 一局结束后应该怎样描述自己的打法？
- My-game 与普通自动清屏型幸存者 Like 的差异是什么？
- 本次设计强化还是削弱“三角色接力解决不同空间压力”的核心？

### 7.3 反目标

- 明确不希望出现什么玩法？
- 哪些旧系统不得恢复？
- 是否会使一名角色成为唯一主 C、其余角色只当按钮？
- 是否会引入新的货币、第三套解锁入口或重复成长轴？

### 7.4 约束

- 单人或小团队的内容生产能力；
- Godot 运行时、1280×720 基线和输入设备；
- 密集战斗性能边界；
- 旧存档、设置、成就和发布兼容；
- 现有美术、动画、音频和测试资源。

### 7.5 成功与停止条件

- 哪个玩家行为发生变化才算成功？
- 哪项现有行为必须保持？
- 什么证据会否定设计？
- 何时停止继续加功能，转入验证？

### 7.6 产品定位与外部参照

- 同类游戏已经建立了哪些玩家预期？
- 本次借鉴的是底层问题解法，还是只复制表面表现？
- 它如何强化 My-game 的差异，而不是使项目更像同类产品？
- 平台、输入设备、语言长度、本地化和商店展示会受到什么影响？
- 商业模式和长期进度是否尊重玩家时间，是否把重复刷取误当成留存？
- 外部参照、玩家评价或市场判断是否有可核查来源，还是团队内部印象？

## 8. L1：十种状态域

每个机制先标出它读取和修改的状态域。

| 状态域 | 内容 | 必问问题 |
| --- | --- | --- |
| **E 存在** | 玩家、敌人、弹丸、领域、掉落物、UI、临时对象 | 谁被生成和销毁？对象池、存档和上限如何处理？ |
| **K 身份/结构** | 角色、技能、敌种、阶段、构筑类别、装备身份 | 它是什么？与相似对象如何区分？结构会否迁移？ |
| **X 空间** | 位置、方向、距离、范围、轨迹、地图边界 | 玩家能预判命中区吗？空间变化是否产生策略？ |
| **R 关系** | 目标、持有者、绑定、阵营、状态附着、配方锁 | 谁影响谁？共享还是独占？关系何时断开？ |
| **V 数值/资源** | 生命、经验、能量、冷却、骨头、等级、倍率 | 来源、上限、消耗、溢出和回收是什么？ |
| **C 控制** | 当前角色、自动/鼠标攻击、动作锁、AI控制 | 谁拥有控制权？何时转移？玩家能否取消或恢复？ |
| **H 信息** | HUD、预警、文本、音效、伤害数字、结算 | 玩家何时看见？能否区分原因、结果和重要级别？ |
| **Q 时间** | 冷却、延迟、持续时间、波次、阶段、单局节奏 | 触发窗口多长？时间压力与反馈是否匹配？ |
| **P 权限** | 解锁、冷却门禁、护盾、互斥、N层开放 | 为什么可用或不可用？权限变化是否明确？ |
| **M 决策** | 角色、目标、卡牌、路线、技能时机、重试 | 谁选择？依据是什么？另一选项造成何种反事实结果？ |

### 状态所有权

对每项关键状态额外记录：

- 所有者；
- 读取者；
- 修改者；
- 生命周期；
- 局内重置还是永久保存；
- HUD 和角色面板中的显示位置；
- 无效、丢失、重复应用和旧档迁移策略。

## 9. L2：25 个状态变化元素

### 9.1 建立

| 元素 | 设计检查 |
| --- | --- |
| 生成 | 生成什么、为何生成、数量和上限是什么？ |
| 放置 | 谁决定位置，是否有空间代价和预警？ |
| 连接 | 状态、目标、角色、技能和奖励如何建立关系？ |
| 揭示 | 何时把隐藏信息告诉玩家，提前量是否足够？ |
| 解锁 | 解锁条件、入口、结果和永久性是否唯一且明确？ |

### 9.2 撤销

| 元素 | 设计检查 |
| --- | --- |
| 移除 | 谁被清除，是否有死亡、回收或结算反馈？ |
| 断开 | 目标、状态或绑定结束时是否留下脏状态？ |
| 消耗 | 消耗谁的资源，玩家是否知道机会成本？ |
| 隐藏 | 信息为何消失，是否会让玩家误判？ |
| 锁定 | 冷却、动作、路线和权限锁是否有明确原因与时长？ |

### 9.3 改写

| 元素 | 设计检查 |
| --- | --- |
| 替换 | 新状态与旧状态差异是否可感知？ |
| 位移 | 距离、方向、碰撞、地图边界和无敌如何处理？ |
| 旋转 | 瞄准轴、扫射、环射和视觉朝向是否一致？ |
| 标量调整 | 数值变化是否改变决策，还是只有账面增长？ |
| 控制权转移 | 玩家、角色或AI何时接管，过渡是否可靠？ |
| 延迟 | 预警、等待和结算之间是否形成预判而非迟钝？ |

### 9.4 转移与流动

| 元素 | 设计检查 |
| --- | --- |
| 耦合位移 | 跟随、牵引、轨道和附着对象如何同步？ |
| 转化 | 伤害、击杀、时间如何转成经验、能量或永久资源？ |
| 分配 | 团队共享、角色独占和目标分配是否清楚？ |
| 检测 | 命中、距离、阈值、时间和击杀检测是否可靠且可解释？ |
| 随机选择 | 随机池、保底、排除、刷新和坏运气边界是什么？ |
| 行为者选择 | 玩家选择与自动选择分别发生在哪里？ |

### 9.5 重构

| 元素 | 设计检查 |
| --- | --- |
| 合并 | 多个效果以何种顺序、加法或乘法合并？ |
| 交换 | 角色、位置、资源或装备交换后谁继承状态？ |
| 分裂 | 弹丸、目标、敌人或奖励分裂后如何防止递归和重复结算？ |

### 9.6 单机制标准描述

每个重要机制用同一条因果句描述：

```text
前置状态
→ 触发者执行动作
→ 权限检查
→ 支付成本
→ 改变目标状态
→ 直接反馈
→ 下游影响
→ 结束、重置或持久化
```

如果无法用这条句式说明，机制通常还没有被定义完整。

## 10. L3：从机制元到生态

### 10.1 机制链

追踪一次动作的完整因果路径：

```text
输入/事件 → 门禁 → 成本 → 状态变化 → 命中/结果 → 奖励 → 反馈
```

检查：

- 是否存在入口但没有结果；
- 是否有结果但没有反馈；
- 是否有文本声称发生、源码实际没有发生的步骤；
- 是否存在旁路，绕开成本或权限；
- 是否在读档、暂停、切场景后断裂。

### 10.2 机制循环

至少标出：

- 正反馈：成功如何提高后续成功概率；
- 负反馈：领先如何受约束；
- 恢复环：失败后如何回到可操作状态；
- 消耗环：资源从哪里来、流向哪里；
- 学习环：行动、结果、解释和下一次改进是否闭合。

每个循环必须回答：

- 玩家多久完成一次；
- 中断条件是什么；
- 是否会雪球失控或陷入死亡螺旋；
- 是否有唯一最优循环；
- 玩家能否感知循环正在运转。

### 10.3 机制网络

把多个循环放在同一张关系表中：

- 哪些资源竞争；
- 哪些机制互相放大；
- 哪些机制互相反制；
- 哪个节点是单点故障；
- 删除某个系统后核心循环是否仍成立；
- 是否出现多个入口实现相同功能。

### 10.4 机制生态

生态不等于内容数量。只有当机制互相改变彼此价值时，才形成生态。

检查：

- 敌种组合是否改变角色和构筑价值；
- 玩家行为是否改变敌人、地图或资源环境；
- 不同角色是否能为其他角色创造条件；
- 构筑是否产生新的处理方式，而非只提高数值；
- 无尽难度是固定开环、玩家反馈闭环，还是两者混合；
- 复杂交互是否仍然可读、可测试、可维护。

## 11. L4：玩家体验的十二个视角

### 11.1 心智模型与可读性

- 玩家知道当前发生了什么吗？
- 操作前能预测，操作后能确认吗？
- 能区分状态来源、持有者和剩余时间吗？
- 规则能否在战斗中快速复述，而非依赖长篇悬停？

完整信息链：

```text
看见状态 → 理解条件 → 预测结果 → 执行动作 → 确认结果 → 归因收益
```

### 11.2 能动性与决策质量

真实选择必须同时具备：

- 至少两个可行选项；
- 结果存在显著差异；
- 存在机会成本；
- 玩家拥有判断依据；
- 选择结果能够被感知。

检查自动攻击、随机发牌和推荐功能是否替玩家做掉了核心决定。

### 11.3 操作、战术与战略技巧

- 操作：走位、瞄准、躲避、技能执行；
- 战术：击杀顺序、切人窗口、技能和大招时机；
- 战略：整局角色投资、构筑路线、阮石和Boss准备。

构筑应决定“擅长怎样解决问题”，操作应决定“能否成功执行”。

### 11.4 风险、收益与公平

- 高收益对应什么风险？
- 威胁是否提前显示？
- 玩家是否拥有至少一种合理反制？
- 惩罚是否与错误程度相称？
- 失败后能否知道具体原因？
- 是否存在屏外、无预警或不可恢复的伤害组合？

### 11.5 反制与反事实

- 如果玩家不执行该动作，会发生什么？
- 另一张卡、另一名角色或另一颗石会怎样解决同一问题？
- 敌人是否迫使玩家改变解法？
- 所有问题是否最终都被“更高伤害/更大AOE”解决？

### 11.6 反馈与感官编排

检查五段反馈：

```text
预备 → 释放 → 命中 → 结果 → 长期收益
```

反馈按重要性而不是数量排序：

1. 致命威胁和玩家重伤；
2. Boss阶段变化；
3. 满能切换和登场；
4. 大招与关键技能；
5. 击杀和暴击；
6. 普通命中。

视觉、音频、文字和动画不可互相矛盾。性能限流应优先保留关键事件。

### 11.7 节奏、张力与释放

- 平稳、压力、预警、高潮、恢复是否交替；
- 是否因持续震屏和爆炸产生感官适应；
- 升级弹窗是否过度打断战斗；
- 冷却、换位能量、大招和Boss窗口是否形成不同时间尺度；
- 高潮后是否有足够恢复和理解时间。

### 11.8 注意力与认知负担

区分：

- 常驻信息：生命、当前角色、关键冷却；
- 条件信息：满能、濒死、Boss转换；
- 查询信息：完整属性、构筑、祝福、装备。

任何时刻同时要求玩家处理的信息都必须纳入注意力预算。

### 11.9 构筑身份与策略拓扑

- 早期是否出现构筑种子；
- 中期是否形成放大器和循环；
- 后期是否出现玩法质变或完成件；
- 选项是数值差异还是打法差异；
- 是否有死卡、万能卡、伪分支、前置干旱和单角色垄断；
- 玩家能否在结算时用一句话描述本局构筑。

### 11.10 失败、学习与重试

完整学习环：

```text
形成假设 → 选择 → 实战 → 结果 → 解释 → 下一次假设
```

检查死亡原因、有效构筑、未用资源、未选路线、快速重试和重开摩擦。

### 11.11 动机与重玩

分别检查：

- 胜任感：我学会了什么；
- 自主感：这是我的选择；
- 发现感：另一条路线会怎样；
- 进展感：下一目标是否明确；
- 表达感：这局打法能否形成身份。

永久成长不得把失败简化为“还需要多刷数值”。禁止用强制日常、损失厌恶或不透明概率代替游戏本身的重玩价值。

### 11.12 角色幻想、叙事和主题一致性

- 最优打法是否符合角色身份；
- 名称、动画、声音、数值和实际策略是否指向同一幻想；
- 剧情和世界内容是否强化玩家正在执行的机制；
- 是否存在“名字是控制，实际只是伤害”的语义错位。

## 12. L5：系统全景检查

每次完整评审都对下表逐项给出“受影响/不受影响/待验证”。

| 系统 | 核心问题 |
| --- | --- |
| 输入与控制 | 键位、模式切换、取消、动作锁和输入冲突是否明确？ |
| 移动与空间 | 速度、碰撞、地图边界、镜头和预警是否支持判断？ |
| 三角色轮转 | 三人是否都有情境价值？切换成本、资源归属和登场收益是否可读？ |
| 普攻、主动技能和大招 | 三个价值层级是否清楚？技能是否具有独立用途和反制对象？ |
| 伤害、治疗、状态和资源 | 结算顺序、来源、叠加、上限和派生触发是否可靠？ |
| 构筑和等级天赋 | 入口是否唯一？候选是否相关？路线是否形成身份？ |
| 祝福、装备和技能解锁 | 多个成长轴是否重叠？绑定、配方和材料锁是否清楚？ |
| 敌人和敌群组合 | 每种敌人制造什么问题，如何识别和反制？ |
| 精英、小Boss和最终Boss | 是否承担阶段考试，而非仅增加生命？ |
| 波次和难度 | 时间曲线、N层缩放、压力上限和恢复窗口是否合理？ |
| 奖励和掉落 | 奖励是否与风险、构筑阶段和局势需要匹配？ |
| 骨头与阮石 | 来源、消耗、升级节奏、单槽排他和长期通胀如何？ |
| HUD、菜单和角色面板 | 当前动作所需信息是否即时，完整信息是否可查询？ |
| 教程和新手流程 | 是否教授规则、判断依据和失败恢复，而不只教授键位？ |
| 结算和重试 | 能否解释本局、形成下一局计划并快速重开？ |
| 音频、特效和镜头 | 关键事件是否拥有分层反馈且不会造成疲劳？ |
| 无障碍和舒适度 | 字号、颜色、键盘焦点、震动、闪烁、音量和模式提示是否安全？ |
| 主线、营地和内容 | 是否服务核心循环，还是形成孤立内容岛？ |
| 存档、设置和成就 | 状态生命周期、迁移、幂等和断点恢复是否完整？ |
| 性能和实体预算 | 是否保持玩法等价？低FPS时优先舍弃什么反馈？ |
| 资产、授权和发布 | 新资源能否合法发布，是否增加发布前替换负担？ |
| 平台、输入和本地化 | 键鼠/手柄、输入图标、文本扩张和不同语言是否仍可用？ |
| 产品定位与商业边界 | 是否强化项目差异，长期进度是否尊重玩家时间？ |

## 13. L5：My-game 的整局生命周期

一项设计不能只在独立测试场景成立，还要放回完整12分钟无尽流程。

| 阶段 | 体验目标 | 必查问题 |
| --- | --- | --- |
| 进入前 | 形成目标 | N层、阮石和继续/新开规则是否明确？ |
| 前30秒 | 建立控制感 | 玩家是否迅速理解移动、攻击方向和当前角色？ |
| 0—3分钟 | 形成构筑种子 | 是否发生有效换位，第一次选择是否给出方向？ |
| 3分钟小Boss | 第一次考试 | 奖励是否放大已有方向，而非随机打断？ |
| 3—6分钟 | 建立循环 | 三角色、主动技能和资源循环是否开始协同？ |
| 6分钟强袭 | 中场高潮 | 精英和小Boss叠加是否可预判、可处理、可恢复？ |
| 6—9分钟 | 改变安全解法 | 远程、冲锋、肉墙、蜂群和领域是否迫使适应？ |
| 9分钟小Boss | 完成形态 | 玩家是否知道自己的最终构筑和Boss计划？ |
| 9—12分钟 | 执行考试 | 是否检验已学能力，而非持续加入新规则？ |
| 最终Boss | 最大释放 | 阶段、护盾、输出窗和三角色价值是否成立？ |
| 结算/死亡 | 解释结果 | 玩家知道做了什么、什么有效、为何失败吗？ |
| 营地/重试 | 形成下一目标 | 是否能快速重试、换石或尝试未选路线？ |

故事模式或未来模式可以使用不同时间轴，但仍须覆盖“进入—学习—形成方向—接受考试—复盘—重试”。

## 14. L6：制作、技术和长期维护

任何方案都要回答：

### 14.1 最小实现

- 能否删除旧入口或复用现有系统？
- 是否真的需要新资源、新货币、新UI或新存档字段？
- 能否先用一个角色、一个敌种或一个N层验证？

### 14.2 内容成本

- 每增加一个节点，需要多少文案、特效、音频、图标和行为回归？
- 组合数量是否导致测试指数增长？
- 是否产生只能服务一个机制的专用资产？

### 14.3 技术风险

- 是否增加 `player.gd`、`enemy.gd` 等中心脚本职责？
- 是否影响伤害事件去重、对象池、批处理或性能保护？
- 暂停、读档、重进场景和倍速下是否仍成立？

### 14.4 数据与迁移

- 状态放在哪里；
- 旧档如何规范化；
- 无效或废弃字段如何处理；
- 失败保存和重复结算如何避免；
- 开发者模式是否会污染正式档案。

### 14.5 可验证性

- 是否存在稳定ID；
- 是否能建立最小自动测试；
- 是否需要图形模式人工检查；
- 是否需要多局数据而不是单次演示；
- 回滚是否简单。

# 第三部分：分析与设计流程

## 15. 阶段 A：建立评审任务

### 步骤 A1：建立评审记录

从 [`design-reviews/TEMPLATE.md`](design-reviews/TEMPLATE.md) 复制一份：

```text
docs/design-reviews/YYYY-MM-DD_主题.md
```

先填写：

- 一句话问题；
- 必须做出的决定；
- 范围与非范围；
- 目标玩家和体验；
- 基准提交；
- 负责人和评审人；
- 预期完成条件。

### 步骤 A2：锁定当前事实

按顺序检查：

1. `graphify-out/GRAPH_REPORT.md` 和图谱新鲜度；
2. `docs/README_文档索引.md`；
3. 对应系统文档、`PRODUCT.md`、`DESIGN.md`；
4. 当前源码的真实入口、门禁、状态变化和保存路径；
5. 对应测试、运行日志和已知问题；
6. 当前工作区差异和上游版本。

输出“来源—主张—证据标签—可信度—冲突”表。

### Gate A：证据就绪

只有满足以下条件才进入设计讨论：

- 当前行为与目标行为已经分开；
- 关键入口、状态所有权和生命周期已经追踪；
- 文档冲突已经列出；
- 缺少的证据被明确标为待验证；
- 没有把历史规划当作当前实现。

## 16. 阶段 B：完整诊断

### 步骤 B1：定义玩家问题

不得写“让它更好玩”作为问题。改写为可观察行为，例如：

- 玩家无法判断满能切换消费谁的能量；
- 多数玩家在一局中只使用一名角色；
- 法师范围技能命中率低，但玩家不知道是预判失败还是判定不一致；
- 玩家死亡后无法说出下局准备改变什么。

### 步骤 B2：建立状态和机制清单

使用十状态域与25变化元素，记录：

- 前置状态；
- 触发和权限；
- 成本；
- 状态变化；
- 反馈；
- 下游影响；
- 重置与持久化。

只为本次范围内的重要机制写详细卡片，不复制整个项目。

### 步骤 B3：追踪链、环、网络、生态

至少输出：

- 一条玩家动作链；
- 一条资源流；
- 一个正反馈环；
- 一个约束或恢复环；
- 与相邻系统的依赖；
- 可能出现的唯一最优、死循环或旁路。

### 步骤 B4：玩家体验十二视角检查

每个视角填写：

- 当前表现；
- 玩家可能形成的心智模型；
- 证据；
- 风险；
- 待验证假设。

### 步骤 B5：系统全景和生命周期检查

逐项标记系统影响，并把机制放回完整单局时间轴。任何只在开发者模式中成立、却无法自然进入正式一局的设计，不得视为完成。

### 步骤 B6：查找退化模式

至少检查：

- 单一最优策略；
- 无效选择和伪分支；
- 资源无限循环或长期溢出；
- 单角色主C垄断；
- 通用数值吞掉角色特色；
- 反馈过载或关键反馈被性能限流；
- 永久成长覆盖玩家技巧；
- 教程、UI和规则不一致；
- 存档、暂停、倍速、切场景和高密度边界；
- 内容与测试成本不可持续。

### Gate B：诊断就绪

诊断必须形成：

```text
玩家可观察的问题
→ 对应机制链断点
→ 跨系统根因
→ 玩家与产品影响
→ 当前证据及不确定性
```

没有根因时不得直接进入大规模方案设计。

## 17. 阶段 C：综合与方案设计

### 步骤 C1：给发现排序

| 等级 | 标准 |
| --- | --- |
| **P0** | 核心承诺断裂、真实规则矛盾、存档/数据安全、不可公平反制、正式流程不可达 |
| **P1** | 高频循环的可读性、角色价值、构筑身份、失败学习或性能等明显受损 |
| **P2** | 在核心稳定后提高深度、新鲜度、演出或长期目标 |
| **P3** | 尚无证据的可选想法，不进入当前实现 |

排序同时考虑影响频率、严重度、证据可信度和修复成本，不用虚假的精确总分。

### 步骤 C2：提出至少三种方向

每次重要评审至少比较：

1. **保持当前**：接受现状会怎样；
2. **删除或最小修复**：能否通过统一规则、删掉重复入口、补反馈解决；
3. **完整方案**：只有最小方案无法满足核心目标时才采用。

必要时再加入实验方案，但不得把“新增更多系统”设为默认答案。

### 步骤 C3：方案比较

| 维度 | 必问问题 |
| --- | --- |
| 玩家价值 | 具体改变哪个行为和体验？ |
| 核心一致性 | 是否强化三角色接力与不同空间解法？ |
| 可读性 | 玩家如何预判、确认和归因？ |
| 决策质量 | 是否产生有代价的真实选择？ |
| 构筑与重玩 | 是否产生新的打法身份和下一局期待？ |
| 公平与反制 | 是否拥有合理应对和恢复窗口？ |
| 系统影响 | 与现有资源、敌人、奖励和UI怎样连接？ |
| 制作成本 | 程序、内容、UI、特效、音频和测试量如何？ |
| 技术风险 | 性能、存档、迁移和组合爆炸风险如何？ |
| 可验证与回滚 | 能否小范围试验，失败后能否撤销？ |

### 步骤 C4：形成设计合同

批准方案必须写成可实现合同：

- 玩家目标行为；
- 前置状态和触发；
- 权限和成本；
- 精确状态变化；
- 时间和空间参数；
- 随机、互斥、上限和保底；
- 视觉、音频、文本和HUD反馈；
- 失败、取消和恢复；
- 局内重置、存档和迁移；
- 与其他系统的接口；
- 明确不做什么；
- 验收标准和回滚条件。

### Gate C：设计就绪

- 方案解决的是根因而非症状；
- 没有创建重复入口或无必要的新成长轴；
- 关键边界和失败路径已经定义；
- 开发、UI、内容、音频和QA能从文档中拆分任务；
- 验收条件可以被观察和验证。

## 18. 阶段 D：验证设计主张

### 步骤 D1：把主张匹配到证据

| 主张 | 最低有效证据 |
| --- | --- |
| 脚本可解析、场景可启动 | Godot headless 解析和启动 |
| 状态变化正确 | 定向 smoke / 单元式行为测试 |
| 存档不丢失或重复 | roundtrip、迁移和幂等测试 |
| 密集战斗行为等价 | 性能基准加玩法计数对比 |
| UI不溢出、预警可见 | 1280×720图形模式或截图检查 |
| 玩家看得懂 | 观察式可用性测试，要求玩家复述规则 |
| 操作公平 | 多次实战、死亡来源和预警窗口记录 |
| 构筑有差异 | 多路线对局与行为/伤害/角色使用对比 |
| 数值平衡 | 跨N层、多局样本而非单次通关 |
| 好玩、爽、想重玩 | 真实玩家重复游玩、访谈和再开行为 |

自动化测试不能证明好玩；一次主观体验不能证明平衡；截图不能证明运行时反馈时序。

### 步骤 D2：先定义假设，再采集数据

示例：

```text
假设：满能换位的能量归属被明确显示后，玩家会更常在合适敌群出现时主动切人，且能准确复述资源消费规则。

观察：满能后的等待时间、满能切换占比、三角色站场时间、玩家口头复述。

否定条件：玩家仍认为能量属于登场角色，或切换频率增加但与敌群无关。
```

### 步骤 D3：最小数据集

在建立大型分析系统前，My-game 的第一批实战记录只需覆盖：

- 版本、run_id、N层、结果、持续时间和最终等级；
- 死亡来源或Boss通关；
- 三角色站场时间和伤害占比；
- 普通切换、满能切换和能量溢出；
- 三角色大招使用次数；
- 最终普通构筑、等级天赋和阮石；
- 骨头获得与消费；
- 玩家对本局构筑和失败原因的一句话描述。

只有当这些数据无法回答设计问题时，才增加更细事件日志。

### 步骤 D4：验证顺序

```text
静态规则检查
→ 最小自动测试
→ headless启动
→ 图形模式短局
→ 完整12分钟对局
→ 多构筑/多N层对比
→ 外部玩家测试
```

后一步不能用来掩盖前一步失败。验证失败后回到对应设计合同或根因，而不是继续增加补丁。

### Gate D：批准实现或实验

状态只能是：

- `approved`：规则已定，可进入完整实现；
- `experiment`：只批准受控原型，不是正式规则；
- `deferred`：方向可能成立，但当前证据或优先级不足；
- `rejected`：已记录拒绝原因；
- `superseded`：被后续记录替代。

## 19. 阶段 E：实现交接和完成回顾

### 步骤 E1：实现交接

评审记录中列出：

- 预计受影响文件；
- 数据和稳定ID；
- UI、特效、音频和文案；
- 自动测试、人工场景和性能检查；
- 存档迁移与回滚；
- 必须同步的长期文档。

实现者可以调整代码结构，但不能静默改变设计合同。发现合同无法实现或成本显著扩大时，回到评审记录更新决定。

### 步骤 E2：实现后验证

- 运行针对性测试；
- 运行项目要求的 Godot 和 graphify 检查；
- 检查真实正式入口，不只测试开发者模式；
- 检查1280×720、键盘焦点、暂停、读档和倍速；
- 对照每条验收标准记录通过、失败或证据缺口。

### 步骤 E3：文档同步

根据改动更新：

- 对应的 `docs/03`—`07` 系统规则；
- `docs/08` 当前实现状态；
- 架构或性能文档；
- `PRODUCT.md` / `DESIGN.md`，若产品或UI约束变化；
- `ROADMAP.md`；
- `docs/KNOWN_ISSUES.md`；
- `docs/RELEASE_CHECKLIST.md`；
- `CHANGELOG.md`。

禁止只更新评审记录而让长期文档继续描述旧规则。

### 步骤 E4：回顾

实装后记录：

- 原假设是否成立；
- 玩家行为和体验发生了什么变化；
- 哪些副作用未被预测；
- 保留、调整、回滚或继续观察；
- 后续问题是否需要新的独立评审。

# 第四部分：评审组织方式

## 20. 评审角色

小团队中同一人可以承担多个角色，但“提出方案”和“质疑方案”应分成两个检查阶段。

| 角色 | 责任 |
| --- | --- |
| 问题负责人 | 建立记录、限定范围、整合决定 |
| 玩法评审 | 检查核心循环、角色价值、决策和构筑 |
| 工程评审 | 检查当前事实、状态所有权、存档、性能和实现成本 |
| 体验评审 | 检查HUD、教学、反馈、音频、无障碍和注意力 |
| 验证评审 | 检查假设、测试、实战场景、数据和验收标准 |

不要求所有人参加所有评审，只邀请真正受影响的职责。

## 21. 会前材料

会议前必须已经具备：

- 一句话问题和目标决定；
- 当前行为证据；
- 机制链或状态变化表；
- 根因和不确定性；
- 至少保持当前、最小修复和完整方案；
- 推荐方案及反对理由；
- 最小验证方式。

没有这些材料的会议只做问题澄清，不作实现决定。

## 22. 会议顺序

1. **目标与范围**：这次必须决定什么；
2. **事实核对**：当前到底怎样工作；
3. **玩家问题**：可观察问题是什么；
4. **根因链**：断点在哪里，影响哪些系统；
5. **方案比较**：包括保持当前和最小方案；
6. **风险挑战**：最优策略、认知、存档、性能、成本；
7. **决定**：批准、实验、延期或拒绝；
8. **验收与责任**：谁做什么，用什么证明完成。

## 23. 评审记录在仓库中的生命周期

标准状态流：

```text
draft
→ evidence_ready
→ review
→ approved / experiment / deferred / rejected
→ implemented
→ verified
```

`superseded` 可以从任何已作出决定的状态进入，但必须链接替代它的新记录。

仓库规则：

- 一份记录只处理一个能够清楚决定的问题；范围扩大时拆分新记录。
- `draft` 和 `evidence_ready` 不是批准，不能被系统文档写成当前正式规则。
- `experiment` 只允许受控原型；默认不得写入永久档案或正式发布路径。
- `approved` 后若精确规则发生实质变化，先更新记录并重新评审，不得在实现中静默改设计。
- 实现提交或PR应引用对应评审记录及验收项。
- `implemented` 只表示代码已进入正式入口；通过匹配主张的验证后才能标记 `verified`。
- 系统长期文档记录最终正式规则；评审记录保留问题、方案、异议和决定历史。
- 已批准记录不通过重写删除异议；更正事实时注明日期和原因，方向替换使用 `superseded`。

## 24. 讨论纪律

- “更爽”“更有深度”“更丰富”必须改写成玩家行为和可观察结果。
- 先说事实和影响，再说解决方案。
- 不用节点数量、系统数量或特效数量替代体验价值。
- 未知问题转成假设和验证，不用争论强行得出结论。
- 反对意见和被拒方案必须记录，避免后续重复争论。
- 发现范围扩大时拆出新评审，不把所有问题塞进一个方案。

# 第五部分：评价和完成标准

## 25. 0—4成熟度量表

只用于发现薄弱项，不默认计算总分。

| 分数 | 含义 |
| --- | --- |
| **0 缺失/矛盾** | 正式流程不可达，或源码、UI、教程和文档互相冲突 |
| **1 存在但弱** | 有机制，但玩家难以理解、选择或感知收益 |
| **2 功能成立** | 基本可玩，规则和反馈能够工作，但深度或证据有限 |
| **3 清晰有效** | 机制、体验和系统关系清楚，多数边界已验证 |
| **4 证据充分** | 多局、多路线或真实玩家证据支持，且技术与内容成本可控 |

建议分别评估：

- 核心承诺一致性；
- 心智模型与可读性；
- 能动性和决策质量；
- 操作、战术和战略深度；
- 风险收益与公平；
- 反馈与感官层级；
- 节奏和注意力；
- 角色差异与轮转必要性；
- 构筑身份；
- 敌人反制与生态；
- 失败学习与重玩；
- 局外经济；
- 无障碍；
- 存档、性能和制作可行性；
- 验证成熟度。

每个分数必须附证据和置信度：`高 / 中 / 低`。

## 26. 发现的标准格式

```text
发现：玩家无法区分普通切换与满能登场。
证据：[源码事实] 两者共用主要切换入口；[待验证] 缺少玩家复述数据。
影响：核心三角色接力被理解为普通换人。
根因：资源归属和消费没有完整的预备—释放—结果反馈。
严重度：P0
置信度：中
最小建议：先统一教程和HUD，并区分满能音画反馈，不新增资源。
验证：玩家能准确说明消费谁的能量，并在对应敌群出现时主动使用。
```

## 27. 完成定义

一项重要游戏设计只有同时满足以下条件才算完成：

- 当前行为与批准规则一致；
- 正式玩家入口真实可达；
- 玩家能预判、执行、确认并归因；
- 选择存在有效差异和机会成本；
- 关键风险拥有反制、恢复或明确接受理由；
- 与相邻系统、完整单局和局外循环兼容；
- 存档、暂停、倍速、性能和无障碍边界已检查；
- 自动化和人工验证与主张相匹配；
- 长期文档、变更记录和已知问题已同步；
- 没有尚未处理的实现任务或明确标注的证据缺口。

## 28. 本流程的首次应用建议

建立流程后，优先创建三份独立评审记录，而不是一次性混在一起：

1. **当前成长体系源头统一**：正式每3级等级天赋与残留108技能节点的保留、归档或恢复决定；
2. **三角色换位体验合同**：换位能量归属、普通切换、满能登场、已关闭退场技、教程和反馈统一；
3. **结算—学习—重试闭环**：死亡归因、构筑摘要、角色贡献、骨头变化和快速重试范围。

这三项分别解决“规则是什么”“核心玩点是否被理解”“玩家为何想再来”，应依次评审，避免继续在矛盾基础上增加内容。
